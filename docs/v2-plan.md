# Takl V2 Plan — VPS Deployability + Performance

Goal: take Takl from "local prototype" to something a user can `curl | install`
onto 1–N VPSes, join into a secure cluster, and use for real project scheduling.

Ordered by what actually blocks deployment. Performance work (swiss maps,
left-right) is Phase 4 — it's real, but useless if nodes can't talk securely
across the internet first.

## Phase 1 — Network correctness on real machines (the actual VPS blockers)

Right now two nodes on different VPSes cannot form a working cluster even
with open firewalls:

- [ ] **Stop hardcoding `IP: "127.0.0.1"`** in `cmd/takld/main.go` (passed to both backends). Add `network.advertise_addr` to config; if empty, auto-detect the first non-loopback IP (or use `memberlist`'s advertise logic).
- [ ] **Set `config.AdvertiseAddr`/`AdvertisePort` on memberlist** in `internal/membership`. Behind NAT/cloud networks, bind addr ≠ advertise addr. Use `DefaultWANConfig()` when peers are cross-datacenter (make it a config option: `cluster.profile: lan|wan`).
- [ ] **Advertised sync addr must be reachable**: nodes gossip their `sync_addr` verbatim, so `0.0.0.0:8100` in the config would be gossiped as-is and peers would dial `0.0.0.0`. Substitute the advertise IP when building `NodeMeta`.
- [ ] Split **bind** vs **advertise** for the HTTP API too (bind `0.0.0.0`, advertise public/private IP).
- [ ] Document the port matrix:

  | Port | Proto | Purpose | Expose to |
  |---|---|---|---|
  | 7946 | TCP+UDP | SWIM gossip | cluster peers only |
  | 8100 | TCP | gRPC sync | cluster peers only |
  | 8090 | TCP | HTTP query API | users / reverse proxy |

## Phase 2 — Security (non-negotiable for anything internet-facing)

Today: plaintext gRPC (`insecure.NewCredentials()` in `internal/transport/client.go`),
no HTTP auth, unencrypted gossip. Anyone who can reach port 8100 can inject
arbitrary replicated state into every node.

- [ ] **Gossip encryption** — cheapest win: memberlist has a built-in keyring. Add `cluster.gossip_key` (32-byte base64) to config, set `config.SecretKey`. One shared key per cluster, generated by `taklctl keygen`.
- [ ] **mTLS for gRPC sync** — replace insecure creds with TLS on both `transport.Client` and the server in `cmd/takld/main.go`. Simplest workable model:
  - `taklctl ca init` → generates a cluster CA (stored on the operator's machine).
  - `taklctl ca issue --node node-a` → per-node cert/key.
  - Config: `network.tls: {ca_file, cert_file, key_file}`. Refuse to start with sync bound to a non-loopback address without TLS unless `--insecure-sync` is passed explicitly.
- [ ] **HTTP API auth** — bearer token middleware (`network.api_token`, compare with `crypto/subtle`). Optional `--api-open` for private-network setups. TLS for HTTP can be delegated to a reverse proxy (Caddy/nginx) — document that instead of building it.
- [ ] **Join authorization** — gossip key + mTLS together already gate membership; document that rotating the gossip key evicts unknown nodes.

## Phase 3 — Replication correctness (bugs that bite in production)

- [ ] **Tombstone resurrection** — GC deletes tombstones after 1h regardless of whether peers saw them. A node offline >1h can resurrect deleted rows on rejoin. Fix: track per-peer ack watermarks (highest HLC each known peer has pulled — the sync server already sees this in `PullRequest`) and only GC tombstones below `min(acks)` across live members, with a hard cap (e.g. 24h) for permanently-dead peers combined with `DeleteByNode`.
- [ ] **Checksum blind spots** — `Store.Checksum` hashes only `key/hlc_ts/hlc_seq`, so rows differing in payload/owner/tombstone look identical. Include owner + tombstone + payload hash (e.g. FNV of payload) in the per-row hash. Keep XOR folding — it's order-independent, which is the property that matters.
- [ ] **`DeleteByNode` HLC collision** — it stamps every tombstone with the same HLC; combined with LWW-by-owner tiebreak this is mostly fine, but bump `hlc_seq` per row to keep total order clean.
- [ ] **Placement is advisory only** — `GET /runners/best` reserves nothing; 50 concurrent clients can all pick the same node between agent ticks. Add a **lease** API:
  - `POST /api/v1/placements {project, ttl}` → node picks best runner, writes a `lease` row (new `Kind`) *owned by the answering node*, decrements a local in-memory available-worker shadow, returns `{runner_id, lease_id, expires_at}`.
  - Leases replicate like any row; scoring subtracts active leases from `AvailableWorkers`. Expiry = tombstone after TTL. This is optimistic (two nodes can double-book briefly) but converges and diffuses far better than jitter alone. Do CP-style reservations later only if users actually need them.

## Phase 4 — Performance: the swiss-table / left-right work

Context first: **Go ≥1.24 built-in maps already use Swiss Tables**, so
`map[K]V` is already the fast path — no external dependency needed. The real
hot-path cost in Takl today is that **every HTTP query runs SQLite queries and
JSON-decodes every row**. Fix that and the maps/algorithms actually matter.

- [ ] **In-memory materialized view (`internal/engine/view`)** — keep decoded domain objects (`map[string]model.Runner`, builds-by-project index, images-by-digest index) in RAM. SQLite stays the durable/replication store; the view is rebuilt on boot and updated on every `Put`/`ApplyRemote`.
- [ ] **Left-right (or RCU) for the view** — exactly the right shape here: reads vastly outnumber writes, and writes are batchy (agent tick, sync round).
  - *Option A — atomic snapshot (RCU-style)*: writers clone-on-write the view and `atomic.Pointer.Swap` it. Dead simple, zero read-side coordination, ~1 alloc per write batch. **Recommended first.**
  - *Option B — true left-right*: two view instances, writer flips a read-side arbiter, waits for readers to drain, then applies to the other copy. Zero-allocation steady state, more code, needs per-reader epoch counters. Do this only if profiling shows snapshot cloning matters (unlikely below ~10k runners).
  - Either way, hide it behind `view.Load() *Snapshot` so the API handlers never touch SQLite for reads.
- [ ] **Score from the view** — `handleBestRunner` becomes: load snapshot, filter, score, sort top-K with a bounded heap (`container/heap`, K≈10) instead of sorting all runners. O(n log K) and zero DB I/O.
- [ ] **Cheap incremental checksums** — maintain the per-kind XOR checksum incrementally in the view (XOR is self-inverse: applying a row = XOR out old hash, XOR in new). Turns every sync round's full-table checksum scan into an O(1) read.
- [ ] **SQLite write batching** — agent `Step()` currently does one implicit transaction per row. Wrap each tick in a single transaction; same for sync rounds (ApplyRemote already does this). Biggest DB win available.
- [ ] **Wire format** — payloads are JSON blobs inside protobuf. Fine for now; if profiles show marshal cost, move hot kinds (runner, queue) to proto messages. Don't do this speculatively.
- [ ] Benchmarks in `internal/engine/view` (`go test -bench`) before/after, plus a `taklui` chaos scenario with 1k simulated runners as the regression guard.

## Phase 5 — Packaging & ops (make it installable)

- [ ] **systemd unit** (`deploy/takld.service`): `Restart=always`, `DynamicUser` or dedicated `takl` user, `StateDirectory=takl` for the DB, config at `/etc/takl/takl.yaml`.
- [ ] **Install script** (`deploy/install.sh`): download release binary for the arch, drop unit file, generate node config interactively (`node id`, `join addr`, paste gossip key/token).
- [ ] **Release pipeline** already exists — add `linux/arm64` (cheap VPSes are often ARM) and publish the Docker image to GHCR from `release.yml`.
- [ ] **docker-compose example** for the "one VPS, docker backend" starter case, mounting `/var/run/docker.sock`.
- [ ] **Docs**: `docs/deploy-vps.md` with the 3-node walkthrough — firewall rules (ufw lines for the port matrix), key generation, joining, verifying with `taklctl cluster`.
- [ ] `GET /metrics` (Prometheus): sync round duration, rows applied, checksum mismatches, view swap latency, placement QPS. Plus `debug/pprof` behind the auth token.

## Phase 6 — Make it useful for real projects (V2 features proper)

The Docker backend currently only *observes*; nothing executes work. Minimum to be useful:

- [ ] **Build/job records from real activity**: label convention (`takl.project=<id>`) on containers → populate `ProjectID` (now hardcoded `"none"`), derive Build rows from container lifecycle, fill image digests (currently empty → digest-based affinity is dead code with the docker backend).
- [ ] **Worker accounting**: `ActiveBuilds`/`AvailableWorkers` from actual running takl-labeled containers instead of static capacity.
- [ ] **CI integration recipe**: GitHub Actions/GitLab runner asks `POST /placements`, gets a runner + lease, dispatches over its own channel (SSH/runner-native). Takl stays a *scheduling oracle* — don't build remote execution into V2; that's a V3-sized liability.

## Suggested order & rough effort

| Phase | Effort | Unblocks |
|---|---|---|
| 0 Housekeeping | 0.5 d | CI green |
| 1 Networking | 1–2 d | any multi-VPS use at all |
| 2 Security | 3–4 d | internet-facing deployment |
| 3 Replication fixes | 3–4 d | trustable data |
| 4 Perf (view + left-right) | 3–5 d | scale + fun |
| 5 Packaging | 2–3 d | "users can use it" |
| 6 Real backend | 4–6 d | actual project value |

Phases 1+2+5 are the critical path for "deployable on a VPS". Phase 4 is
independent and can be done in parallel by a second person — it only touches
`internal/engine/view` (new), `internal/api`, and store write hooks.
